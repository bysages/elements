Elements stands on one premise: **interaction is handled, appearance is entirely ours**. Interactive components wrap proven headless state machines; every visual decision — the paper-and-ink design language, the token system, the lighting engine — lives in one style layer, so the whole surface of the library changes together.

## Layers

| Layer      | Technology                            | Owns                                                                 |
| ---------- | ------------------------------------- | -------------------------------------------------------------------- |
| Components | headless state machines               | interaction, state, ARIA, positioning — delegated, unstyled          |
| Styling    | `@bysages/core`                       | the only visual layer: native CSS scoped by `data-scope`/`data-part` |
| Theming    | design tokens → CSS custom properties | palettes, light/dark, contrast and density tiers                     |
| Responsive | native CSS container queries          | components respond to their container, not the viewport              |
| Frameworks | React, Vue, Solid, Svelte             | one component API across all four                                    |

## Anatomy is the contract

Every part carries `data-scope` and `data-part` attributes, plus machine state (`data-state`, `data-open`, …). The stylesheets target those attributes — so one stylesheet serves every framework, and codegen, tests, and agents can rely on a stable shape.

## Tokens are the only source

Colors, spacing, radius, elevation, and motion all resolve from `--bs-*` custom properties. If a value is hardcoded in a component, it is a bug. Themes (accent pigments, scenes, density) are attribute-driven on the root element — `applyTheme` from `@bysages/core` writes them for you.
